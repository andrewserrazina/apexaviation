## 1. Executive Summary

Two confirmed production issues were investigated and addressed at the code/migration level (Priority 1) or fully diagnosed with an operator-safe remediation procedure (Priority 2):

**Priority 1 — Ground School Stripe registration bug (root-caused and fixed in code):** `confirm_scheduled_ground_class_enrollment` has had two overloads since `v57.sql` — a 6-parameter original and a 7-parameter version adding `p_payment_status text DEFAULT 'paid'`. Calling with exactly the 6 shared parameters — precisely what `stripe-webhook` has done since `v57` shipped — is genuinely ambiguous to Postgres's function resolver ("function ... is not unique"), regardless of role, grants, or whether the call uses named or positional arguments with exact type casts. This was reproduced against the live production database (safe, read-only, no-op diagnostic call) and is corroborated by the independent review's finding of a completed/paid $25 Checkout Session with no matching enrollment that was subsequently refunded. **Fixed** by (a) making `stripe-webhook` pass `p_payment_status: 'paid'` explicitly, and (b) `v110`, which drops the now-obsolete 6-argument overload and removes the `DEFAULT` from the surviving 7-argument function, so there is exactly one signature and every future caller must be explicit.

**Priority 2 — Lifecycle cron 401 (root-caused, remediation procedure written, not executed):** Confirmed still live as of the most recent scheduled run (2026-09-04 13:00 UTC, `net._http_response.status_code = 401`). No code or configuration discrepancy was found — `verify_jwt = false` is correctly present in `config.toml`, and the 401 response's `text/plain` content-type matches the function's own `return new Response('Unauthorized', ...)` code path, not Supabase's JSON-formatted platform-level JWT-rejection response. This confirms the request reaches application code and fails purely on a **value mismatch** between the Vault secret (`lifecycle_cron_secret`) and the Edge Function's `LIFECYCLE_CRON_SECRET` env var — the same issue diagnosed in an earlier session, whose fix could not be completed because no tool in this environment can set Edge Function secrets. **A previously-generated rotation value was printed in an earlier chat transcript in that session and must be treated as compromised** — Section 12 below specifies a **fresh** rotation, generated by the operator, never displayed here.

**Neither fix has been applied to production.** All work is source-controlled and locally tested (60/60 automated regression tests pass, including 14 new tests specific to this hotfix).

## 2. Root Cause — Ground School RPC Ambiguity

`public.confirm_scheduled_ground_class_enrollment`:
- `(uuid,text,text,uuid,text,integer)` — created in `v17.sql`, the original.
- `(uuid,text,text,uuid,text,integer,text DEFAULT 'paid')` — added in `v57.sql` for the Ground School pack-enrollment path.

Postgres's function-overload resolver does not disambiguate between "N required parameters" and "N required + 1 defaulted parameter" when a call supplies exactly N arguments — not with positional arguments, not with named arguments (PostgREST's actual call mechanism), and not even with exact type casts on every argument. All three forms were tested directly against this exact function pair and all three produced:
```
ERROR:  function public.confirm_scheduled_ground_class_enrollment(...) is not unique
HINT:  Could not choose a best candidate function. You might need to add explicit type casts.
```
`stripe-webhook/index.ts` has called this RPC with exactly the 6 shared named parameters (no `p_payment_status`) since `v57.sql` shipped, meaning **every real Stripe payment for a scheduled-class Ground School registration has been silently failing at this line since that migration**, falling through to the webhook's own refund-and-alert-admin error handling instead of completing.

## 5. v110 Migration

`portal/supabase-portal-schema-v110-ground-school-rpc-overload-fix.sql`, in order:

**A. Drop the obsolete six-argument overload** (`drop function if exists ...(uuid,text,text,uuid,text,integer)`), confirmed dead code — zero remaining callers, external or internal (Section 7).

**B. Recreate the seven-argument function without the `DEFAULT` on `p_payment_status`.** Postgres refuses a plain `CREATE OR REPLACE FUNCTION` that removes a parameter's default (`cannot remove parameter defaults from existing function`), so this required a `DROP FUNCTION` + `CREATE FUNCTION` instead — wrapped in an explicit `BEGIN`/`COMMIT` transaction so the function is never briefly absent for a concurrent webhook delivery. The body is byte-for-byte identical to the live definition; only the parameter list changes.

**C. Decision on the `DEFAULT`: removed.** Both legitimate callers (`stripe-webhook`, now fixed, and `enroll_in_ground_school_via_pack`, which already passes it positionally) supply `p_payment_status` explicitly after this fix, so the default served no legitimate caller — only the risk that a *future* caller could silently default to `'paid'` without realizing a value was required. Removing it converts that failure mode from "silently wrong" to "fails loudly at call time," which is the safer contract for a payment-status field, per the requested preference for explicitness at every call site.

**Grant re-statement (required, not optional):** because step B is a `DROP` + fresh `CREATE` rather than a same-signature `REPLACE`, the function does **not** inherit its previous ACL — a fresh `CREATE` instead picks up Supabase's project-level default-privileges rule, which would silently re-grant `EXECUTE` to `anon`/`authenticated`, undoing `v104`. The migration explicitly re-applies the `v104` grant state (`REVOKE` from `public`/`anon`/`authenticated`, `GRANT` to `service_role`) inside the same transaction.

After this migration, exactly one function signature exists under this name:
```
public.confirm_scheduled_ground_class_enrollment(uuid, text, text, uuid, text, integer, text)
```
with `p_payment_status` mandatory.

## 10. Affected-Transaction Reconciliation Procedure

**Do not perform customer remediation or charge anyone from this procedure alone — it identifies what needs a human decision, it doesn't make the decision.** No customer PII is included below; the query and its aggregate result are safe to keep in git because they return counts, not rows.

**Step 1 — Supabase-side classification (read-only, safe to run in the SQL editor):**
```sql
select
  case when csa.completed_at is not null and e.id is not null then 'PAID + ENROLLED'
       when csa.completed_at is not null and e.id is null then 'PAID + NOT ENROLLED (needs Stripe refund-status cross-check)'
       when csa.completed_at is null and csa.created_at < now() - interval '24 hours' then 'EXPIRED'
       else 'OPEN'
  end as bucket,
  count(*) as n
from public.checkout_session_attempts csa
left join public.scheduled_ground_class_enrollments e on e.stripe_session_id = csa.stripe_session_id
where csa.purpose = 'ground-school-registration'
group by 1
order by 1;
```
Current result (captured for this report, counts only):

| Bucket | Count |
|---|---|
| PAID + ENROLLED | 0 |
| PAID + NOT ENROLLED (needs Stripe refund-status cross-check) | 1 |
| OPEN | 1 |
| EXPIRED | 7 |

**Step 2 — Stripe-side cross-check (operator must do this in the Stripe Dashboard/API — this repo has no Stripe secret key and must never be given one):** for every row in the `PAID + NOT ENROLLED` bucket, look up that `stripe_session_id`'s PaymentIntent/Charge in Stripe and sub-classify:
- **Refunded** → matches the independently-reported incident; no further action needed on that transaction (the customer already has their money back), but confirm no duplicate attempt exists for the same person/class that *did* enroll (would mean they're both refunded and separately enrolled, worth a courtesy check).
- **Not refunded** → **PAID + NOT ENROLLED + NOT REFUNDED**, exactly the urgent case called out in the approval. This means Apex Aviation is holding a real customer's money with nothing delivered and no refund issued. Requires immediate manual action: either honor the registration (if the class still has capacity and hasn't passed) or refund immediately.

**Step 3 — Extend the same query to the pack-enrollment metadata purpose** if the operator wants to rule out the same failure mode having ever affected `enroll_in_ground_school_via_pack` calls (it should not have, since that path always called the 7-argument form explicitly — but Step 1's query only covers the Stripe-metadata purpose `'ground-school-registration'`; pack enrollments carry `amount_cents = 0` and aren't Stripe transactions in the same sense, so there is no equivalent refund-reconciliation need there).

**Step 4 — After `v110` and the webhook fix are deployed to production**, re-run Step 1's query going forward — the `PAID + ENROLLED` count should start incrementing normally with every completed scheduled-class registration, which is itself the confirmation the fix is working in production (not just in this local harness).

## 11. Lifecycle Cron 401 Root Cause / Configuration Findings

**Confirmed still live**: the most recent scheduled run (`cron.job_run_details`, runid 18, 2026-09-04 13:00:00 UTC) shows `status = 'succeeded'` (meaning only that `pg_net` successfully queued the async HTTP request — this is the well-known `cron.job_run_details` caveat, it does not reflect the downstream HTTP response). The actual response, in `net._http_response` for that same request, is `status_code = 401`.

**No code or configuration discrepancy found.** Specifically checked and ruled out:
- `verify_jwt = false` is present in `portal/supabase/config.toml` for `send-lifecycle-emails` (a documented fix for a *different*, earlier 401 cause — platform-level JWT rejection before the function's own code ever ran — already resolved per that file's own comment).
- The 401 response's `content-type: text/plain;charset=UTF-8` matches the function's own code path exactly (`return new Response('Unauthorized', { status: 401 })` defaults to `text/plain`), **not** the JSON-formatted body Supabase's platform-level gateway returns for a JWT-verification rejection. This is direct evidence the request reaches application code and is rejected by the function's own `Authorization !== \`Bearer ${CRON_SECRET}\`` check — i.e., a pure secret-value mismatch, not a routing or `verify_jwt` problem.
- This matches and confirms the diagnosis from the prior session: the `lifecycle_cron_secret` Vault secret was rotated at that time, but the corresponding `LIFECYCLE_CRON_SECRET` Edge Function secret was never updated to match, because no tool in this sandbox (no `supabase` CLI, no Supabase access token in the environment) can set an Edge Function secret. That gap is still open today, confirmed by this run's 401.

**Important correction to carry forward:** that prior session's rotated value was printed directly in chat output before this Phase 2B's "never print the secret" constraint existed. That value must now be treated as potentially compromised (chat transcripts can be logged/stored) and **must not be reused**. Section 12 specifies generating an entirely new value.

## 14. Rollback Plan

- **`stripe-webhook` code change:** a one-line revert (remove `p_payment_status: 'paid'`) restores the prior (broken) behavior — not recommended, but trivially reversible via redeploying the previous function version.
- **`v110`:** rollback commands are included as a trailing comment block in the migration file itself — restoring the six-argument overload's original body and re-adding the `DEFAULT` to the seven-argument function. Since Postgres has no `ALTER FUNCTION ... ALTER PARAMETER SET DEFAULT`, a real rollback of the default removal requires the same `DROP` + `CREATE` pattern `v110` itself uses. **Rolling back reintroduces the ambiguity bug** — only do this if `v110` itself is found to have broken something, and prefer fixing the real problem over a full rollback if at all possible.
- **No migration in this report touches or deletes application data.** `v110` is a pure function-definition change; the webhook code change affects only future calls, not past rows.
